**关键技术点**（踩坑记录）：

| 坑 | 现象 | 解法 |
|---|---|---|
| 微软禁用 IMAP 基本认证 | 用户名+密码登录被拒 | 必须走 OAuth2：refresh_token → access_token → XOAUTH2 |
| `imaplib.authenticate()` 格式错 | `BAD [b'Command Argument Error. 12']` | 它把凭据当 **literal** 发（`{123}`），XOAUTH2 要裸 base64。改手工发协议 |
| 手工认证后状态机不同步 | `command SELECT illegal in state NONAUTH` | 认证成功后手动 `conn.state = "AUTH"` |

**邮箱文件格式**（`D:\Backup\Downloads\outlook.txt`）：

```
邮箱----密码----clientid----refresh_token----辅助邮箱----辅助邮箱密码
```

字段 [3] 形如 `M.C511_BAY.0.U.MsaArtifacts...`，是 **Microsoft refresh token，不是普通密码**。
15 个账号共用同一个 client_id `9e5f94bc-...`。

- `load_accounts()` 解析清单

### 2. 比特浏览器 —— CDP 打通

**结论：静态代理模式可正常启动，CDP 可被 Playwright 接管**

```bash
python tools/verify_bb_proxy.py      # 4/4 配置对比
python tools/verify_bb_cdp_real.py   # 9/12（3 个 FAIL 经核实不是问题）
```

实测数据：

```
[PASS] 静态_proxyMethod=2  →  CDP http://127.0.0.1:56703  Browser: Chrome/156.0.8078.78
[FAIL] 直连_proxyMethod=3  →  请填写提取URL: dynamicIpUrl
```

**`proxyMethod` 取值含义**：

| 值 | 含义 | 实测 |
|---|---|---|
| 1 | 不使用代理 | 未测 |
| **2** | **自定义静态代理（host/port/user/pass）** | **✅ 可启动** |
| 3 | 直连 | ❌ 动态IP套餐下报错，要 dynamicIpUrl |
| 4 | 动态IP | 需 `dynamicIpUrl`（提取链接） |

**套餐开通前后对比**：

| 阶段 | 启动返回 |
|---|---|
| 开通前 | `code=11018 窗口被限制打开`（RPA 并发为 0） |
| 开通后 | `请填写提取URL: dynamicIpUrl`（并发已放开，只差代理配置） |

**三个"假 FAIL"的真相**（重要，避免误判）：

| 采集值 | 看着像问题 | 实际 |
|---|---|---|
| `webdriver: false` | 以为没隐藏 | **正常**。Chromium 未开自动化时默认就是 false，只有 true 才是破绽 |
| `tz: Asia/Shanghai` | 以为时区没改 | **正确行为**。`isIpCreateTimeZone=true` 让时区**跟随代理出口 IP**。本机 Clash 串的是亚洲节点，所以是上海 |
| `mem: null` | 以为内存没改写 | 影响很小，不强制 |

第二条是**比特浏览器的核心优势**：时区/语言/地理位置自动跟随 IP 地理，从根上杜绝
「美国 IP + 亚洲时区」这种致命矛盾。Playwright 兜底方案做不到这点。

**代码**：`app/register/bitbrowser.py`（API 封装）、`app/register/bb_fingerprint.py`（指纹构造 + 判定）

### 3. IPDEEP 代理 —— 部分打通

**已确认的接口规范**（从官方文档 + 实测）：

```
POST https://openapi.ipdeep.com/openApi/V2/{Controller}/{action}
```

关键：**action 全小写**，参数名 **PascalCase**。

| 接口 | 参数 |
|---|---|
| `/Account/balance` | 无 |
| `/Account/traffic` | 无 |
| `/DynamicProxy/countries` | `ProxyType` |
| `/DynamicProxy/states` | `ProxyType`, `CountryCode` |
| `/DynamicProxy/cities` | `ProxyType`, `CountryCode`, `StateCode` |
| `/DynamicProxy/updateDynamicPassword` | `DynamicPassword` |

`ProxyType` 取值：`dynamicDataCenter` / `dynamicResidential` / `mobile`

请求结构（OpenApiRequest）：

```json
{
  "key": "API Key",
  "timestamp": 1731306000000,
  "nonce": "GUID",
  "data": "AES加密后的Base64",
  "sign": "签名"
}
```

- `aesKey = SHA256(key + secret).Substring(0, 32)`
- AES-CBC + PKCS7，前 16 字节是 IV
- `ResData` 返回值也是加密的，需同 key 解密

**目前状态**：路径对了、结构对了，只差 `sign` 算法。

```
POST /openApi/V2/Account/balance
→ {"ErrCode":"10006","ErrMsg":"Sign Is Invalid"}
```

返回 10006 而不是 404，说明**请求已经被应用层识别**，只差签名。

已穷举 60+ 种签名组合（MD5/SHA256、各种拼接顺序、key/secret 前后缀、HMAC、含/不含 language），全部 10006。

**踩过的坑**：一度以为 `md5(sorted_kv + secret)` 是对的（返回 10005 Duplicate Request），
后来发现那是因为**共用同一个 nonce** 导致的重复请求，不能证明签名正确。必须每次用新 nonce 才能判定。

## 二、卡点与下一步

### 卡点：IPDEEP 的 sign 算法

两条路，**推荐第二条**：

#### 方案 A：拿后台账号密码

登录 `user.ipdeep.cn`，用文档页的"发送请求"功能发一次真实请求，
从浏览器网络面板抓到正确的 `sign`，反推算法。

需要你提供：**IPDEEP 后台的登录账号 + 密码**

#### 方案 B：后台生成"提取链接"（推荐）

你说得对，**比特浏览器原生支持 `dynamicIpUrl`**，直接填一条提取链接，
比特浏览器自己调用来换 IP，根本不用我逆向 sign。

操作步骤：

1. 登录 `https://user.ipdeep.cn`
2. 进「动态代理」页面
3. 找「生成链接」/「API 提取」/「复制链接」按钮
4. 配置：地区（US）、协议（http）、提取数量（1~5）、粘性时长（30 分钟）
5. 复制生成的链接发我

拿到链接后我直接填进比特浏览器的 `dynamicIpUrl`，配置变成：

```python
proxy_fields = {
    "proxyMethod": 4,          # 动态IP模式
    "dynamicIpUrl": "https://...提取链接...",
}
```
