# Qoder 积分发放机制与批量注册链路调查报告

> 整理日期：2026-11-07
> 版本：v2.0（邮箱路线重定位版）
> 归档路径：`D:\qoder_register\docs\report.md`

---

## 1. 结论摘要

1. Qoder 的"一机一号"限制，代码层判的是**客户端自报的本地设备标识**（Machine ID / Telemetry ID / MAC / 卷序列号 / SafeStore），不是不可伪造的硬件证明。标识存在本地、可写，就能被重置。
2. 注册阶段（网页）与领取阶段（桌面客户端）走两套互不交叉的风控：网页拼浏览器指纹，客户端拼机器标识，服务端未把两者强绑定。
3. 注册所需身份只有两项：**邮箱 + 图形验证码**。手机号只起抬高单号成本的作用，去掉手机号后单号成本从 ~¥0.5 降到 ~¥0.36。
4. 邮箱身份源有三种可落地形态：**Outlook 别名 / Hotmail 子地址（+tag）/ iCloud「隐藏我的邮件」统一转发**。三者的区别只在"信从哪来、怎么自动取链接"，后面的注册、清设备、领取流程完全一致。
5. 这条链是时间差生意：领到即提走，封号对成本已无影响。要真正堵，只能把设备标识升级为服务端可验证（TPM/EK 公钥绑定），其余手段都是抬成本。

## 3. 链路总览

```
① 出邮箱 → ② 清设备 → ③ 网页注册 → ④ 收信点确认
        → ⑤ 客户端登录领取 300 Credits + 14天Pro
        → ⑥ 提货入库 → ⑦ 换邮箱回 ②
```

| 步 | 动作 | 关键点 |
|---|---|---|
| ① | 从邮箱池取一个未用地址 | 一轮一地址，地址与账号一一对应 |
| ② | 重置 Machine ID / Telemetry ID / MAC / 卷序列号 / SafeStore | 先关客户端再清，否则内存旧值回写 |
| ③ | Playwright 填表注册 | 指纹浏览器环境 + 住宅代理 + 同源 IP 点确认 |
| ④ | 取验证邮件里的确认链接并访问 | 出口 IP 尽量与注册同源 |
| ⑤ | 客户端登录 | 服务端判"新设备" → 发额度 |
| ⑥ | 存 Cookie/Token 或留号 | 入库标注到期日 |
| ⑦ | 回 ② | 循环 |

## 4. 邮箱身份源（三条路线对比）

不掺手机号，邮箱就是唯一身份凭证，因此**收信可靠性 = 整条链的成败**。

### 4.1 路线 A：Outlook + 子地址（`+tag`）

| 项 | 内容 |
|---|---|
| 原理 | `name+tag@outlook.com`，同一收件箱可派生任意多地址 |
| 成本 | ¥0（主号免费） |
| 优势 | 不用买域名；邮件直接落在 IMAP 收件箱，Python `imaplib` 直取 |
| 风险 | Qoder 侧若对 `+tag` 做归一化（去加号后比对），等于同一账号，可能第一号就撞"已注册" |
| 应对 | 每个主号只做 1 个裸地址 + 少量 tag；主号数量横向铺开 |

### 4.2 路线 B：Hotmail 多主号

| 项 | 内容 |
|---|---|
| 原理 | 每个号一个独立 `@hotmail.com` / `@outlook.com` 主地址，不做 tag 派生 |
| 成本 | ¥0（自建）或 ¥1~5/个（向号商买） |
| 优势 | 地址互相独立，不存在归一化撞车 |
| 风险 | 微软对新注册账号有风控（需真实注册、异地登录锁定），自建成本是人工时间 |
| 应对 | 主号提前养（注册后放几天再用于 Qoder），登录用固定 IP |

### 4.3 路线 C：iCloud「隐藏我的邮件」统一转发

| 项 | 内容 |
|---|---|
| 原理 | iCloud+ 的 Hide My Email：为每个网站生成 `xxxxx@privaterelay.appleid.com`，全部转发到同一个 Apple ID 主邮箱 |
| 成本 | iCloud+ 订阅（¥6/月起）内含隐藏地址配额 |
| 优势 | 地址形态是随机串，天然不像模式化批量；全部转发到一个邮箱，**收信只需要轮询一个 IMAP/收件箱** |
| 风险 | 配额有限（随订阅档位，几十到上百）；转发链对发件方 SPF/DMARC 敏感，验证邮件可能被丢弃；`privaterelay.appleid.com` 后缀公开可见 |
| 应对 | 配额内优先用；把 Apple ID 主邮箱设为 Outlook/QQ 等可 IMAP 的地址，统一收信即可覆盖 A/B/C 三条线 |

**核心设计决定**：三条路线都归结为"**一个统一收件箱**"。把 Apple ID 主邮箱、以及各 Outlook 主号，全部配到同一个聚合器里，下游注册脚本只认"收件箱"，不关心信从哪个入口来。

| 维度 | A: Outlook `+tag` | B: Hotmail 多主号 | C: iCloud 隐藏地址 |
|---|---|---|---|
| 单价 | ¥0 | ¥0~5 | 订阅内配额 |
| 地址独立性 | 弱（可能被归一化） | 强 | 强 |
| 收信自动化 | IMAP 直取 | IMAP 直取 | 需转发到可 IMAP 的主邮箱 |
| 地址外观 | 一看即知是别名 | 普通邮箱 | 随机串，最"真" |
| 可扩展量 | 取决于主号数 | 取决于账号库存 | 取决于订阅配额 |
| 首选场景 | 验证归一化不严时 | 批量主力 | 配额内优质地址补充 |

## 5. 注册环节技术要点

1. 从邮箱池取地址 → 状态置 `pending`
2. 分配指纹浏览器环境（Camoufox / AdsPower 窗口）+ 住宅代理出口
3. Playwright 打开注册页，填邮箱、独立强密码、用户名
4. 遇图形验证码 → 打码平台（YesCaptcha / 2Captcha）回填，¥0.01~0.03/次
5. 聚合器轮询/订阅收信 → 抓确认链接 → 用**同源 IP** 访问
6. 账号入库：地址、密码、注册 IP、时间、状态 → `active`

反自动化硬要求：

| 项 | 要求 |
|---|---|
| `navigator.webdriver` | 置 false，补全 `chrome.runtime` |
| TLS 指纹 | `curl_cffi` 走真实 Chrome JA3，不用 requests 默认 |
| 时区/语言 | 与代理地区一致（美国 IP 配 `Asia/Shanghai` 是明显失配） |
| 停留与轨迹 | 加随机停顿，不瞬移鼠标 |
| 密码 | 每号独立，不跨号复用 |
| 验证邮件有效期 | 收到即刻点击，做 webhook 不做慢轮询 |

## 6. 设备标识重置

| 目标 | 位置 / 动作 |
|---|---|
| Machine ID | 应用配置目录 + 注册表对应键，删除或写随机值 |
| Telemetry ID | 本地存储，删除 |
| 硬件指纹缓存 | 应用数据目录下的缓存文件 |
| MAC 地址 | 网卡高级属性 Network Address（Windows）/ `ip link set`（Linux） |
| 磁盘卷序列号 | 卷序列号改写 |
| SafeStore 文件 | 应用数据目录对应文件删除 |

顺序固定：**关客户端 → 清标识 → 再开客户端登录新号**。

| 项 | 单价 | 说明 |

## 10. 平台风控建议（按有效性排序）

### 10.1 设备标识服务端可验证（唯一能根治）

| 措施 | 原理 | 破解难度 |
|---|---|---|
| TPM / 安全芯片 attestation | 标识由硬件密钥签名，服务端验签 | 高 |
| 端侧密钥对 + 首启注册 | 私钥存 TPM/Keychain，服务端绑公钥 | 高（私钥不可导出即不可克隆） |
| 多源硬件交叉哈希 | CPU + 主板 + 磁盘 + TPM EK 公钥 | 高 |
| 客户端完整性校验 | 检测 hook/注入，上报校验和 | 中高 |

### 10.2 领取环节时序风控

| 措施 | 检测内容 |
|---|---|
| 首次领取延迟门槛 | 注册后 N 小时，或需先完成 N 次真实调用 |
| 一致性打分 | 领取设备/IP/支付与首次登录的一致性 |
| 异常沉默模型 | 领完 24h 零调用 → 冻结未消耗额度 |
| 领用时序图 | 多次以"新设备"身份出现但行为模式高度相似 |

### 10.3 跨账号关联

| 维度 | 关联信号 |
|---|---|
| 网络 | IP C 段聚集、住宅代理商业 ASN、JA3/JA4 复用 |
| 账号 | 注册时间聚集、密码相似度、用户名随机串风格 |
| 邮箱 | 同域聚集、`+tag` 归一化后重复、`privaterelay.appleid.com` 聚集 |
| 设备 | Machine ID 生成算法特征（时间戳规律）、硬件字段部分重复 |
| 支付 | 无支付 + 从不付费 + 只领免费额度 |

处置策略：建账号图取连通分量聚合风险分，命中高危簇**延迟发放**，把损失窗口从"已提走"改为"还没到手"。

### 10.4 活动规则收紧

| 措施 | 作用 |
|---|---|
| 试用额度分级发放（首 50，用满再补 250） | 压低一次性可变现价值 |
| 额度与账号强绑定、封号即清零 | 降低二手市场价值 |
| 免费试用也需绑定支付方式（不扣款） | 直接断掉无支付批量号 |
| 注册强制手机验证 | 抬高单号成本，邮箱路线失效 |
| 设备指纹簇限频（超阈值只给半额） | 削弱重置收益 |

### 10.5 监控指标

| 指标 | 阈值建议 | 含义 |
|---|---|---|
| 单 IP 日新注册数 | > 5 告警 | IP 农场 |
| 单设备指纹簇账号数 | > 3 告警 | 设备重置嫌疑 |
| 首日领完率 / 7 日调用率 | > 10 告警 | 纯薅不用户 |
| 同邮箱域账号数 | > 20 告警 | 别名农场 |
| 领取→封号时延中位数 | 持续下降 | 对抗升级 |

## 11. 脆弱点

1. **收信道是命门**。主邮箱被锁或转发链被丢信，前面全废；因此聚合器要支持多后端冗余。
2. **`+tag` 归一化风险**。一旦平台做去加号比对，路线 A 直接失效，必须能无缝切到 B/C。
3. **代理质量决定成败**。机房 IP 成批死，住宅代理涨成本。
4. **重置工具会过时**。平台换标识算法或加完整性校验，工具跟不上就断。
5. **iCloud 配额天花板**。路线 C 无法无限扩量，只能做补充。
