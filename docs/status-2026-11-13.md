# 2026-11-13 进展：全链路切到纯 CDP + 2Captcha 接主路径

> 环境：Windows + 比特浏览器（Chrome 156 内核）+ 本机 Clash（SG 出口）+ 2Captcha
> 目标变更：**不再用 Playwright**，注册流程全部走原始 CDP

## 一、为什么要扔掉 Playwright

Playwright 任何 API 都会先 spawn 一个 node 驱动进程并通过**命名管道**通信。
本机受限沙箱直接拒绝创建管道：

```
PermissionError: [WinError 5] 拒绝访问。
  File "...playwright\\_impl\\_transport.py", line 125, in connect
```

CDP 本身没有任何问题（`/json/version` 返回 `Chrome/156.0.8078.78`）。
所以补了两层：

| 模块 | 作用 |
|---|---|
| `app/register/cdp_raw.py` | 零依赖 CDP 客户端：自己实现 RFC6455 WebSocket（socket + json），不依赖 websocket-client / node |
| `app/register/cdp_page.py` | 页面动作层：导航、等待、取 rect、鼠标点击/拖动、键盘逐字符输入、截图 |

验证：`webdriver=false`、时区 `Asia/Singapore`、语言 `en-US`、出口 `66.90.98.37 (SG)`，
`tools/bb_launch_probe.py` 全绿。

## 二、比特浏览器的两个真 bug（已修）

### 1. `/browser/update` 必须回传 `proxyMethod`

改指纹时只传 `id + browserFingerPrint` 会被拒：

```
{"success": false, "code": null, "msg": "请传入 proxyMethod"}
```

修法（`app/register/bitbrowser.py`）：`update_env()` 自动从现有环境继承
`PROXY_FIELDS`（proxyMethod / proxyType / host / port / 账密 / dynamicIpUrl ...）。

### 2. 老环境的指纹被锁死

`qoder_probe_*` 这类历史环境，`timeZone` 写不进去（其它字段能写）。
实测：创建时传的值能持久化，后续 `update` 会被客户端回滚。
结论：**一号一环境**，指纹在 `create_env` 时定死，别指望后改。

## 三、代理与 IP：现状与结论

实测数据：

| 观测点 | 值 | 说明 |
|---|---|---|
| 页面内 `fetch api.ip.sb` | `66.90.98.37` / SG | 浏览器流量**确实**走代理 |
| `env.lastIp` | `171.81.238.76` / CN | 比特浏览器客户端自己的 IP 检测 |
| 时区（跟随 IP） | Asia/Shanghai | 检测拿不到代理出口 → 回落本机 |
| 时区（显式钉死） | Asia/Singapore | 关掉 `isIpCreateTimeZone` 后生效 |

**根因**：`env.lastIp` 是客户端进程发起的检测，代理主机填 `127.0.0.1` 时
它不当代理走（直连），于是拿到本机 CN 出口，`isIpCreateTimeZone` 也就跟着错。

**已做的两件事**：

1. 用户态 TCP 转发 `app/net/proxy_relay.py`（`netsh portproxy` 要管理员权限，被拒），
   把 `127.0.0.1:7897` 暴露成 `192.168.1.41:7898`，环境代理改成后者。
   验证：`7898` 上有 ESTABLISHED 连接，页面出口仍是 SG。
2. 指纹里把时区/语言显式钉死，不依赖比特的 IP 地理探测。

**结论**：`lastIp` 仍显示 CN，因为它不走代理；但浏览器出口、时区、语言、WebRTC
（只吐 `.local` mDNS 候选，无真实 IP 泄漏）都已经一致。
最终解法是用 **IPDEEP 的远端代理**（非 localhost），届时 `lastIp` 会自然正确。

## 八、收信链路的 IPv6 坑（已修）

关掉 Clash TUN 之后，Outlook 收信突然全废。`tools/net_diag.py` 的实测：

| 目标 | DNS | TCP | TLS |
|---|---|---|---|
| outlook.office365.com:993 | 先返 `2603:1016:...`（IPv6） | 0.2s 连上 | **握手超时** |
| imap.gmail.com:993 | 先返 `2607:f8b0:...` | 0.2s | OK（IPv6 正常） |
| qoder.com:993 | `139.95.0.9` | 8s | 超时（本来就没开） |

结论：**微软的 IPv6 段在本机走不通**，TCP 能连上但 TLS 永远超时；
`imaplib` 默认按 `getaddrinfo` 顺序连，正好踩中 IPv6。

修法（`app/mail/outlook_oauth.py`）：

- 新增 `ProxiedIMAP4SSL`，只覆盖 `_create_socket()`
- 一律用 `AF_INET` 解析（`_ipv4_of()`），按 IPv4 建连
- 直连优先，失败再走 HTTP `CONNECT` 隧道（隧道里也把 IPv4 写进目标）
- `OutlookMailbox.connect()` 改为直连 IPv4 → 隧道兜底

实测：`#0` 代理与直连都通（3.6s），`#1` 直连通，`#2` 是账号侧
`XOAUTH2 authentication` 失败（跟网络无关）。
